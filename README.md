# Fraud Detection with SQL: Rule-Based Transaction Monitoring

A SQL project that builds and tests rule-based transaction monitoring queries on the PaySim mobile money dataset. The final rules catch **99.6% of fraud with only 5 false positives**.

**Author:** Preeti Punia
**Tools:** SQL (SQLite), DB Browser for SQLite
**Dataset:** PaySim synthetic mobile money transactions

---

## Business Problem

Financial crime teams review alerts generated by monitoring rules. A good rule has to catch fraud (**recall**) without burying analysts in legitimate transactions (**false positives**). This project designs rules in SQL and measures each one on both.

## Dataset

PaySim simulates mobile money transactions with a fraud label (`isFraud`). Fraud occurs only in `TRANSFER` and `CASH_OUT` transactions, so the analysis focuses on those two types (about 2.77 million transactions, 8,213 of them fraud).

Key columns: `type`, `amount`, `oldbalanceOrg`, `newbalanceOrig`, `oldbalanceDest`, `newbalanceDest`, `isFraud`.

## Approach

1. Built Rule 1 from a typical fraud pattern (an account emptied in one transaction) and measured precision and recall.
2. Examined the fraud the rule missed, then tested each candidate rule on the **full table**, not a sample.
3. Kept rules that were precise, rejected rules that flagged far too many legitimate transactions.
4. Stopped when the remaining fraud had no pattern that could be isolated without overwhelming false alerts.

## Rules and Results

| Rule | Logic | Fraud caught | False positives | Decision |
|---|---|---|---|---|
| R1: Account drain | `amount = oldbalanceOrg` and `newbalanceOrig = 0` | 8,024 | 0 | Keep |
| R2: Zero-balance sender | `oldbalanceOrg = 0` and `amount > 0` | 25 | 1,308,541 | Rejected |
| R3: Overdraw to zero | `amount > oldbalanceOrg` and `newbalanceOrig = 0` | 4 | 1,180,062 | Rejected |
| R4: Fixed 10M amount | `amount = 10,000,000` | 145 | 0 | Keep |
| R5: No balance movement | TRANSFER, sender balance unchanged, destination balance 0 before and after | 13 | 5 | Keep |

(R2 to R4 were tested on transactions that Rule 1 did not already flag.)

### Final performance (R1 + R4 + R5)

| Metric | Result |
|---|---|
| Total fraud | 8,213 |
| Fraud caught | 8,182 |
| Fraud missed | 31 |
| Recall | **99.6%** |
| False positives | 5 |
| Precision | **99.9%** |

## Example Query: Rule 1 with recall and false positives

```sql
SELECT type,
       COUNT(*) AS total_txns,
       SUM(isFraud) AS total_fraud,
       SUM(CASE WHEN amount = oldbalanceOrg
                 AND newbalanceOrig = 0
                 AND isFraud = 1 THEN 1 ELSE 0 END) AS caught,
       SUM(CASE WHEN amount = oldbalanceOrg
                 AND newbalanceOrig = 0
                 AND isFraud = 0 THEN 1 ELSE 0 END) AS false_positives
FROM transactions
WHERE type IN ('TRANSFER','CASH_OUT')
GROUP BY type;
```

## Key Findings

- One simple rule (account drain) catches about 98% of fraud with zero false positives.
- Rules that look sensible, such as zero-balance senders or overdrafts, would generate over a million false alerts each, so they were rejected.
- The remaining 31 missed cases (zero-balance senders, overdrafts, partial withdrawals) share patterns with millions of legitimate transactions. Leaving them uncaught is a deliberate trade-off between detection and analyst workload.
- Testing on a small sample (`LIMIT 20`) gave a misleading picture. Every rule was validated on the full data.

## Limitations

- PaySim is **synthetic**. Its fraud follows patterns built into the simulation, so results are cleaner than real-world data, and real monitoring would need tuning against many more false positives.
- The 10,000,000 amount in Rule 4 appears to be the simulation's maximum transfer. In a real system, an equivalent rule would target amounts just below an actual policy limit.
- Rules were designed and tested on the same dataset, with no separate hold-out set.

## Skills Demonstrated

SQL aggregation, conditional aggregation (`CASE WHEN` inside `SUM`), filtering and grouping, precision and recall analysis, rule design and validation, and communicating trade-offs.

## How to Reproduce

1. Download the PaySim dataset (CSV) and import it into SQLite as a table named `transactions`.
2. Open the project in DB Browser for SQLite (`paysim1.sqbpro`).
3. Run the queries in the Execute SQL tab.
